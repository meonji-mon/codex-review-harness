# 메인의 검수 배정·수정·종료 절차

적용 조건: `AGENTS.md` 7절에 따른 검수를 배정하거나 결과를 합칠 때. 이 문서는 메인용이며 검수자에게 전체를 전달하지 않는다. 검수자는 자신의 좁은 계약과 역할만 받는다.

## 무엇을 배정하는가

독립 검수는 `AGENTS.md` 7절의 고위험 변경에 자동으로 의무 적용한다. 사용자가 요청한 검수는 별도의 필수 완료 조건이다. 그 외에는 메인 선택 검수로 분류한다.

| 실제 변경 | UI 검수 | 코드 검수 |
|---|---|---|
| 고위험 변경, 화면·사용자 흐름에 영향 있음 | 의무 | 의무 |
| 고위험 변경, 화면 영향 없음 | 해당 없음 | 의무 |
| 사용자가 검수를 명시한 변경 | 요청한 역할은 필수 | 요청한 역할은 필수 |
| 고위험이 아닌 화면·코드·설정·자산 변경, 별도 검수 요청 없음 | 선택 | 선택 |
| 동작·산출물에 영향 없는 설명 문서 | 별도 요청 때만 | 별도 요청 때만 |

고위험은 인증·권한·결제의 판단/처리, 데이터 삭제/이관, 공유 API 호환성 파괴, 앱 시작 불가·핵심 흐름 중단·서명/운영 환경 오류의 구체적 위험이다. 위 고위험 항목의 구체적 가능성이 있고 관련 근거를 확인해도 위험을 배제할 수 없으면 고위험으로 본다. 일반적인 요구의 모호함만으로 고위험으로 분류하지 않는다. 메인은 분류 이유를 한 줄로 남긴다.

사용자 요청은 필수 검수로 처리한다. 메인 선택 검수는 같은 증상의 반복 실패를 원인 재검토했거나 그 밖의 구체적인 근거로 필요하다고 판단한 경우에 쓴다. 선택 검수를 호출하지 않은 역할을 `PASS`나 `NOT_APPLICABLE`로 꾸미지 말고 ‘비고위험으로 생략’이라고 기록한다. 검수 생략은 메인의 관련 검사·UI 직접 조작·기존 배포 조건 면제가 아니다. 선택 검수에서 확인된 결함은 의무 검수와 같게 처리한다.

검수자의 모델은 해당 역할에 대한 사용자 지정이 있으면 이를 우선하고, 없으면 지원되는 GPT-6 Astra 또는 GPT-6 Sol과 기본 effort `high`를 호출에 명시한다. 상향은 필요 근거와 지원을 확인한 경우에만 한다. 메인의 모델만 지정된 경우 이를 검수 모델 선택으로 확대하지 않는다. TOML이 모델·effort를 고정하지 않으므로 호출 전후 유효값을 확인하고 암묵적 상속에 의존하지 않는다. 실제 실행기가 명시 선택을 지원하지 않거나 선택값을 확인할 수 없으면 미확인으로 보고한다. 역할별로 하나씩만 배정하며, 수를 맞추려고 에이전트를 만들지 않는다. 동시 실행이 불가능하면 순서대로 수행한다. 사용자가 두 역할의 검수를 명시하면 두 역할에 범위를 전달하되 실제 적용 대상이 없을 때만 해당 없음을 보고한다.

## 입력을 분리한다

먼저 사용자 요구·보존할 동작·변경 파일·검수 완료 기준과 필요한 증거를 정한다. 작은 작업은 기존 브리프에 몇 줄로 적으면 충분하다. [인계 템플릿](packet-template.md)을 사용할 수 있지만 모든 칸을 형식적으로 채우는 문서 작업을 만들지 않는다.

검수 스냅샷에는 커밋과 관련 dirty diff/untracked 파일의 식별, 설정·빌드·증거의 대응을 넣는다. 비밀값을 담은 파일이나 전역 계정 설정은 검수 자료로 묶지 않는다. 관련 파일이 검수 중 달라지지 않도록 조정한다. 다른 작업이 변경한 파일을 지우거나 되돌려 스냅샷을 맞추지 않는다.

UI 검수자는 요구·프로토타입·화면·조작 증거부터, 코드 검수자는 요구·diff·관련 계약·테스트/추적부터 받는다. 메인의 원인 확정 서술이나 “통과해 달라”는 결론은 넣지 않는다. 이미 알려진 실패는 숨기지 말고 관찰 사실·재현 조건으로 전달한다. 각 검수자의 첫 판정이 나오기 전 서로의 결론은 공유하지 않는다.

## 별도 하네스를 실제로 적용한다

Codex가 사용자 정의 에이전트를 지원하면 이름 `ui_reviewer`와 `code_reviewer`를 지정하고 각 TOML의 독립 지침이 적용됐는지 확인한다. TOML에는 [공통 계약](reviewer-contract.md)과 해당 [UI](ui-reviewer.md) 또는 [코드](code-reviewer.md) 하네스가 인라인으로 포함돼 있다. 동일 본문을 다시 매번 첨부하지 않는다.

해당 로더를 쓰지 못하는 환경에서는 실제 제공되는 별도 에이전트 기능에 공통 계약과 역할 본문을 직접 전달할 수 있다. 존재하지 않는 호출 API·옵션·역할 이름을 만들어 실행했다고 표시하지 않는다. 별도 에이전트 자체를 실행할 수 없으면 메인의 자체 점검만 수행하고 독립 검수는 미수행으로 남긴다.

[활성화 기준](activation.md)의 역할 적용·컨텍스트 전달·검수 입력을 실제 기록으로 확인한다. `CONFIRMED`만 의무 독립 검수로 인정한다. 단순한 새 이름·스레드·다른 모델·자기 진술을 근거로 삼지 않는다. 확인 수단이 없으면 미확인/미지원으로 종료하고 새 근거 없는 재호출을 하지 않는다. 상위 지침과 프로젝트 보안 규칙은 유지한다.

`read-only` 설정과 `[agents].enabled=false`는 각 서브의 기본 구성이다. 부모 런타임 오버라이드, 도구별 접근권한, 설정 로딩 결과를 실제로 확인한다. 광범위한 쓰기 권한이 남아 있으면 검수자를 쓰기 도구에 노출하지 않는 구성이 필요한지 먼저 판단한다. 검수자는 안전한 증거 읽기만 수행하고, 메인은 실제 제한이 확인되지 않은 상태를 기술적으로 차단된 샌드박스라고 보고하지 않는다. 이 패키지 적용을 이유로 계정·MCP·pool·전역 권한 설정을 무단 수정하지 않는다.

## 실행과 증거

메인이 관련 테스트·빌드·스크린샷·안전한 재현 자료를 준비한다. 기본 검수는 `evidence-only`이며 원본 파일·로그를 독립적으로 읽는다. 이 결과는 직접 테스트 실행이 아니다. UI가 직접 조작해야 하는 기준은 격리된 환경이 준비됐을 때만 `isolated-ui`로 넘기며, 그렇지 않으면 필요한 조작 증거를 메인이 확보한다.

메인은 [인계 양식](packet-template.md)의 검사 원장을 전달한다. 이번 작업의 성공·실패·취소·타임아웃·재시도와 필요하지만 미수행한 검사까지 원본 실행 기록에 연결한다. 실패 후 성공한 결과만 남기지 않는다. 긴 로그는 다시 복사하지 말고 접근 가능한 원본 참조를 준다.

검수자는 허용된 작업 실행 기록·CI 결과·원본 로그를 원장과 대조하고 변경된 테스트·검사 설정도 읽는다. 검수 범위 밖 이력이나 비밀값을 조사하지 않는다. 기록 수집 범위 밖의 실행, 로그 누락·삭제·잘림, 확인할 수 없는 재시도는 숨기지 않는다. 목록이나 해시만으로 누락이 없다고 증명하지 않는다. 필수 기준의 증거를 확인할 수 없으면 최소 추가 증거를 요청하고 `INCONCLUSIVE`로 남긴다.

두 검수자가 같은 정적 스냅샷을 읽는 것은 병렬로 진행할 수 있다. 같은 시뮬레이터·브라우저 탭·계정 상태를 바꾸거나 성능 측정에 영향을 주는 작업은 직렬화한다. 새로운 실행 환경·테스트 계정·프로파일러 설치는 검수자의 일이 아니다.

## 결과 통합과 재검수

수행 대상으로 정한 역할의 판정을 받으면 범위·스냅샷·필수 증거·독립성부터 확인한다. 유효한 `PASS`만 해당 역할의 통과로 인정한다. `NOT_APPLICABLE`에는 실제 비대상 이유가 있어야 한다. 필수 증거 부족을 임의로 적용 대상 없음으로 바꾸지 않는다.

메인이 같은 원인의 지적을 합치고 우선순위와 재검증 경로를 정한다. UI의 성공 관찰과 코드의 위험 지적이 다르면 입력·상태·시간 조건을 비교해 근거를 보완한다. 다수결이나 모델의 이름으로 결론을 선택하지 않는다. 재현 근거 없는 지적은 그 이유를 기록해 비차단 가설로 분리하며, 확인된 결함을 일정이나 취향 때문에 임의로 기각하지 않는다.

수정은 메인 또는 지정된 구현 담당이 역할 제한과 파일 소유권 안에서 수행하며 최종 책임은 메인에게 있다. 검수 역할은 수정 담당을 겸하지 않는다. 수정 diff와 바뀐 증거를 원래 검수자에게 넘겨 해당 결함 및 영향받은 기준을 재확인한다. 동일한 스냅샷에 새 근거 없이 같은 전체 검수를 반복하지 않는다. 원래 검수자가 재개될 수 없으면 최소 인계로 새 검수자에게 해당 범위만 넘기고 교체 사실을 남긴다.

고위험 의무 검수·사용자 요청 필수 검수의 누락이나 확인된 차단 결함이 남으면 로컬 구현과 실행한 검증은 각각 보고하되 해당 변경의 완료 판정·병합·배포는 보류한다. 필수 판정이 충족되면 기존 승인·TestFlight 조건으로 돌아가고, 검수 자체를 새 배포 승인으로 취급하지 않는다. 메인 선택 검수의 실행 불가만으로 새 의무 관문을 만들지는 않는다. 다만 실제 차단 결함이나 원래 필수였던 검증 누락은 해결하거나 미완료로 보고한다. 종료 보고에는 수행한 역할의 실제 판정과 핵심 근거, 생략한 역할의 이유만 덧붙인다.
