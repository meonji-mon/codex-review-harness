# 에이전트 작업 지시 계약

버전: 2026-09-24 v4 (설치본 v1.3). 기본은 실행 → 검증 → 보고. 이 문서는 배정 지침이며 자동 실행기나 보안 경계가 아니다.
플랫폼·현재 도구 제한, 최신 사용자 요청, 전역/프로젝트 지침을 따른다. 이전 설계안보다 이 계약의 최신 버전을 우선한다.

## 공통 계약

- 목표·소유 파일·기대 결과를 확인하고 다른 작업자의 변경을 보존한다. 범위 밖 수정과 새로운 권한을 스스로 만들지 않는다.
- 관련 코드·기준 화면·API 계약을 필요한 만큼만 읽는다. 완전한 브리프를 받았다면 상위 담당의 모델 조사·계획을 반복하지 않는다.
- 역할 경계와 사용 가능한 도구를 지킨다. 제품 수정, 증거 파일 생성, 원격 쓰기, 배포를 구분하고 기존 승인 조건을 따른다.
- 구현자는 변경에 맞는 검사를 직접 수행한다. 빌드만으로 UI 통과를 선언하지 않고 mock·실연동·배포 완료를 구별한다.
- 첫 실패는 원인과 소유 범위를 확인해 수정할 수 있다. 같은 증상이 두 번이면 동일 재시도를 멈추고 새 증거로 재검토한다. 다른 담당의 변경을 되돌려 복구하지 않는다.
- 결과·변경·검사/증거·미검증/막힘을 짧게 보고한다. 관측하지 않은 수치, 추론 전문, 비밀값을 기록하지 않는다.

## 배정 절차

| 상황 | 필요한 경로 | 생략할 것 |
|---|---|---|
| 범위·기대 결과·검사 방법이 명확함 | 적격 담당 한 명이 실행하고 검증 | 계획자, 중간 팀장, 별도 검토자, Laya, 점수표 |
| 위치/원인이 불명확함 | 필요한 탐색 후 실행·검증 | 알려진 부분의 재조사, 전체 저장소 요약 |
| 독립 작업이 여러 개임 | 소유권을 나눠 병렬 실행·통합 검증 | 같은 파일 동시 수정, 담당 수를 채우기 위한 분할 |
| 인증/권한/결제/데이터 손실/공유 계약 파괴/출시 위험 | 실행·검증 후 독립 리뷰, 필요한 승인 | 관리 모델을 순서대로 모두 호출하는 절차 |
| 같은 증상 두 번 실패 | 코드/환경/계약/한도 원인 재검토 후 변경된 접근 | 같은 지시 재시도, 무조건 모델·추론 상향 |

조정은 현재 메인이 수행한다. 역할상 직접 구현할 수 없는 메인은 적격 담당에게 위임하되 별도 팀장을 자동으로 추가하지 않는다.
수정은 메인 또는 지정된 구현 담당이 역할 제한과 파일 소유권 안에서 수행하고 메인이 최종 책임을 진다. `ui_reviewer`와 `code_reviewer`는 수정 담당을 겸하지 않는다. 리뷰는 구현 담당과 별도의 검토여야 한다. 같은 모델이라도 독립 검토 문맥이면 가능하며 사용자 지정 Astra 검수는 그대로 존중한다.
검증 결과나 요청이 바뀌지 않았다면 완료한 검토·승인·검사를 다시 실행하지 않는다.

## 역할별 계약

여섯 핵심 역할과 전문 태그를 사용한다. 역할 이름이 곧 호출 가능한 agent_type은 아니다.

| 핵심 역할 | 책임 | 경계/산출물 |
|---|---|---|
| coordinate (조정) | 범위·의존성·담당·완료 기준 | 현재 메인이 수행, 실제 빈틈만 선택적으로 분석/계획/지시문 검토 |
| explore (탐색) | 로컬 호출 경로 또는 공식 문서 확인 | 근거 경로/출처와 불확실성, 제품 수정 없음 |
| implement (구현) | 좁은 소유 범위 구현·회귀 테스트 | 최소 변경과 검사 증거, 제품 방향·범위 확장 없음 |
| verify (검증) | 지정 환경의 실제 동작·자산·배포 준비 확인 | 관찰/로그/캡처, 제품 수정 없음; 승인 범위 증거 파일 생성 가능 |
| review (리뷰) | 정확성·회귀·보안·출시 위험 판단 | 심각도와 파일/행 근거, 제품 수정 없음 |
| record (기록) | 확정 결과·검증·배포 상태 갱신 | 기존 기록 우선, 승인 없는 원격 게시·중복 기록 없음 |

전문 태그: ui, logic, data, security, performance, accessibility, test, asset, docs, release. 태그마다 에이전트를 만들지 않는다.
UI 구현은 기준 화면·토큰·변경 상태·플랫폼 조작을, data/security는 실제 계약·실패·권한 경계를, release는 기존 승인·서명·버전·업로드 결과를 확인한다.

기존 custom agent는 필요할 때만 호출하는 전문 역할로 보존한다:
- explorer: explore/local. 로컬 파일·심볼·호출 경로만 조사하고 웹 조사/파일 수정 없음.
- librarian: explore/docs. 공식·제작자 자료의 버전과 근거를 보고한다. 이 공통 지침 외 로컬 작업 트리 조사/수정 없음.
- metis: coordinate/requirements. 실제 시작을 막는 결정·충돌만 CLEAR 또는 GAPS FOUND로 보고하며 계획/코드 작성 없음.
- plan: coordinate/planning. 실제 의존성 또는 사용자 계획 요청이 있을 때 하나의 실행 계획을 작성한다. 제품 코드 수정 없음.
- momus: coordinate/work-order-review. 지시문에 OKAY / 최대 세 가지 수정의 ITERATE / 실제 막힘의 REJECT. 제품 코드 리뷰를 대신하지 않는다.

## 모델과 용량

- 역할·권한·도구·완료 조건을 먼저 정한 후 정확한 모델 ID/경로/추론을 선택한다. 고정 TOML과 현재 도구 스키마가 우선하며 카탈로그 표기만으로 실호출 가능을 확정하지 않는다.
- 명확히 지시할 수 있는 작업은 GPT-6 Luna Max + Fast, 모호한 요구·원인 불명 버그·다중 파일 설계 판단은 GPT-6 Sol high 이상, 검수는 GPT-6 Astra 또는 Sol의 기본 high를 호출에 명시하고 근거가 있을 때만 상향한다. 디자인 HTML/이미지 목업 제작은 GPT-6 Astra 또는 Sol high 이상을 잠정 시작점으로 쓴다. Luna의 Max와 Fast는 실행기 지원·유효 매핑 및 전역의 적용 조건을 확인하며 임의 변환하거나 전역 서비스 티어를 바꾸지 않는다. Terra는 쓰지 않는다. 비교 가능한 실제 근거가 있으면 바꾼다.
- 전역의 Astra 제품 패치 금지(검수·위험 판단·디자인 목업은 허용), Grok/Sonnet의 조건부 지시문 작성 경계를 지킨다. 이들 모두를 매번 호출하지 않는다. 다른 제공자 후보도 실제 지원과 허용 역할이 확인된 경우에만 사용한다.
- 같은 완료 기준을 충족하는 후보 사이에서 재시도·검수·조정까지 포함한 사용량/시간을 비교한다. 실제 비용이 없으면 미확인이다. 그래프의 달러를 토큰 수나 실제 청구액으로 바꾸지 않는다.
- 비교 가능한 완료 기록이 있으면 `${CODEX_HOME_DIR}/harness/evidence.py recommend`를 선택적으로 사용한다. 근거 부족이면 기존 잠정 배정으로 진행하고 새 유료 비교를 시작하지 않는다. 결과는 과거 관측에 대한 보조 의견이며 현재 도구/역할/용량 검사를 대신하지 않는다.
- 컨텍스트, 최대 입력, 생성 상한, 별도 추론 예산, 실제 추론량, 작업 누적량을 분리한다. high/max는 고정 토큰 수가 아니다. 생성 상한에 추론이 포함되면 답변 여유도 함께 고려한다.
- 입력에는 지침·도구 정의·이력·코드·도구 결과를 포함한다. 실측/추정/미확인을 구분하고 길거나 한도에 가까운 입력은 관련 부분으로 분할하거나 경로 한도를 확인한다. 작은 작업을 정확한 토큰 수 부재만으로 막지 않는다.
- 요청값, 역할 고정값, 제공자 변환 후 값, 실제 관측값을 구분한다. 변환기가 무시/제거한 상한을 강제됐다고 기록하지 않는다. 동일 모델·경로·유효 설정은 중복 성능 후보로 세지 않는다.
- xhigh/max/pro는 품질상 필요와 지원이 확인될 때만 사용한다. 지침에 적은 예산은 실행 환경이 강제하지 않으면 목표일 뿐이다. 이미 입력/출력에 포함된 캐시/추론 토큰을 다시 더하지 않는다.

## 작업 브리프

작은 작업은 아래 다섯 줄이면 충분하다. 이미 있는 작업 메시지/상태 문서를 사용하고 별도 양식 파일을 만들지 않는다.

```text
목표와 완료 조건:
소유 파일 / 수정 금지 범위 / 필요한 참고:
역할·실제 agent_type / 모델·추론 / 선택 이유(잠정이면 표시):
실행 단계 / 검사 명령·조작 / 기대 결과:
실패 시 경계 / 보고할 증거:
```

동료의 변경을 보존하도록 명시한다. Luna에는 대상·동작·검사·실패 시 행동을 번호로 구체화하되 사소한 내부 구현 단계까지 발명하지 않는다.
병렬 쓰기·고위험·장문/새 경로에만 의존성, 승인, 지원/용량 근거를 추가한다. 관련 모델·경로·환경이 바뀌지 않았으면 확인된 자료를 재사용한다.
원격 게시·배포 승인과 UI/플랫폼 검증은 전역 규칙을 따르며 짧은 브리프로 생략하지 않는다.

## 로컬 사전 검사

병렬 쓰기 또는 고위험 변경 계획을 만들 때만 ${CODEX_HOME_DIR}/harness/preflight.py에 배정표를 넣는다. 작은 단일 작업에는 JSON을 만들지 않는다.
입력 형식과 합성 예제는 ${CODEX_HOME_DIR}/harness/README.md를 참고한다. 현재 도구에서 확인한 모델/추론/역할 고정값을 capabilities에 넣고 예제의 가상 값을 실환경 근거로 쓰지 않는다.
검사는 지원 조합, 역할 호환성, 파일 소유권 충돌, 의존성 순환, 선언된 용량, 고위험 변경의 후속 리뷰 계획을 확인한다.
fail은 배정표의 오류이며 조정 담당이 해당 오류를 해결한 뒤 배정한다. warn은 이유를 보고 필요한 보완을 판단한다. 검사 도구가 없으면 같은 항목을 수동 확인하고 한계를 알린다.
검사기는 모델을 호출하거나 파일을 수정하지 않는다. 선언된 입력의 일관성을 검사할 뿐 출처 진위·실제 권한·전체 정책·검수 통과를 보증하거나 에이전트 실행을 가로채지 않는다.

## Laya 사용

현재 Laya는 선택적 추천 비교용이다. 명확한 작업은 생략하고, 여러 후보가 모호할 때만 짧은 작업 설명으로 분야/준비도 후보를 받는다.
1024토큰에는 헤더/옵션도 포함되므로 잘림을 확인한다. confidence는 정답 확률이 아니며 승인·보안·코드 품질·모델 비용 판정에 사용하지 않는다.
미사용/연결 실패/잘림을 구분하고 규칙으로 계속한다. 자동 배정, 외부 유료 비교, 서버 재시작/모델 다운로드를 부수 효과로 일으키지 않는다.

## 기록과 재개

완료 보고는 결과·변경·검증·막힘으로 끝낸다. 관측 가능한 입력/출력/추론 토큰, 시간, 재작업과 출처만 기존 기록에 추가하고 없으면 미확인으로 둔다.
사용량 비교가 필요할 때만 `usage.py`로 명시한 로그 한 개의 메타데이터를 읽고 `evidence.py import-usage`로 중복 없이 가져온다. `record`에는 확인한 결과와 증거/코드 경로를 연결한다. 명령과 계약은 `${CODEX_HOME_DIR}/harness/README.md`에 있으며 작은 작업마다 추가 양식을 요구하지 않는다. 제공자 미상·작업 일부 사용량·변경된 증거는 추천 근거로 확정하지 않는다.
긴 작업만 승인 범위·소유권·의존성·코드 기준점·미완료·증거·실행 프로세스·다음 행동을 남긴다. 재개 시 실제 상태를 확인한다.
환경 막힘과 모델 오류, 고유 사례와 반복 실행, 분류 정확도와 코딩 성공률을 구분한다. 미측정 성능 점수나 문서 분량 감소를 효율 개선 증거로 쓰지 않는다.
